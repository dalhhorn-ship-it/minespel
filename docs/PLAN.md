## How to read this

* **Group** is a wave. Group A runs first, then B, and so on. Tasks in the same group touch different files and can run at the same time, once their own dependencies are done. A task may start before its group when all its dependencies are done, but **a task never starts while another running task lists any of the same files**. This matters most for `src/main.ts`, `src/game/game.ts`, `src/ui/hud.ts`, `src/app/screens.ts` and `scripts/check-dist.mjs`.
* When a group is big, start the tasks of the earliest milestone first.
* **Files**: the only files the task may create or change. A listed `x.ts` includes its test `x.test.ts` next to it. A CSS file is imported by the `.ts` file of its screen (`import './x.css'`), so no other file changes for it. E2e hooks are registered inside the feature's own file, so no extra hook file is needed. In a parallel group, `CHANGELOG.md`, `README.md` and `docs/ARCHITECTURE.md` are updated by the operator from the developer's report.
* **(stub)** after a file means: create it as a placeholder that shows "Komt nog" with the final exported function. A later task replaces it.
* **Acceptance** lists PRD `AC` numbers. Each task proves them with tests (unit or e2e) unless marked (iPad), which is a check by hand on the real iPad.
* Every task: `./scripts/check.sh` passes, tests added, no new packages (only T1 edits `package.json`).

* **T18 backup format.** One JSON object: `{ app: "dino-blokwereld", format: 1, createdAt: <ISO time>, appVersion, schemaVersion, kv: {...}, stores: {...} }`. `kv` holds settings, player, world, dinos, economy, rotation, switches, stats, meta and village. Left out: `gate` (pincode and lockout), `worldV1` (the kept 0.4.0 copy), `session` (a running break or exam) and `timers`. `stores` holds every row of progress and ownModules as `[key, value]` pairs, and every row of answers, breaks, exams and ledger with its `id`. Typed arrays (only `world.diff` today) are written as `{ "$u32": "<base64>" }` by one generic encoder and decoder. The file name is `dino-blokwereld-backup-JJJJ-MM-DD.json` in local time (helper `backupFileName(now)`). `buildBackup` reads everything in one readonly transaction and makes no network request (unit: a stubbed `fetch` that throws is never called). `markBackupMade(now)` writes `meta.lastBackup` and is called only after the share sheet or the new view reports success.
* **T18 check.** `checkBackup(text)` returns the data or one friendly Dutch message, and never throws. Order: text over 20 MB, not JSON, wrong `app`, `format` or `schemaVersion` higher than this build ("Dit bestand is van een nieuwere versie. Werk de app bij."), then every record against the save rules. Rules are reused, not copied: dino names as the name screen allows (`filterDinoNameDraft(name) === name`, at most 12 characters), so `<b>Pip</b>` and `https://x.nl` fail; points a whole number of 0 or more; shop dinos at most `MAX_SHOP_DINOS` (`shopDinoCount`) and chickens at most `MAX_CHICKENS` (`chickenCount`); settings inside the ranges of 4.17 (volume 0 to 1); every world diff entry valid as `cleanDiff` reads it (none dropped); found rare blocks 34 to 41; log rows are plain objects with a whole number `id`. Unknown `kv` names are refused. Older shapes need no extra code: restore writes the records as they are, and the normal load path (record defaults, the v11 world upgrade for a world without `terrainVersion`) moves them on the next start, as for any old save. Fixture `tests/fixtures/backups/v050-old-shapes.json`: a 0.4.0 world, `malus` ledger rows, no `fluit`, no `pointsMode`. Plus one fixture per bad case of AC130 and AC195.
* **T18 one safe replace.** `replaceAll(db, data | null)` in `backup.ts` uses a new `haltWrites()` switch in `db.ts`: once set, every other readwrite transaction is refused quietly (the save queue keeps its dirty flags; nothing lands). Then one readwrite transaction over all 7 stores reads the current `gate`, clears every store, writes the backup (or nothing, for Alles wissen), and on restore puts the same `gate` back, sets `session` to null and `timers` to the default, and writes `meta` with this build's `schemaVersion` and `appVersion` and `lastBackup` set to the file's `createdAt`. All parsing and checking happen before the transaction opens, and nothing but IndexedDB requests is awaited inside it. IndexedDB undoes the whole transaction if the app is killed, so the old data stays (AC197). Writes queued before the halt finish first, because IndexedDB runs overlapping readwrite transactions in order. A test only option `afterClear?: () => void` runs inside the transaction right after the clear, so unit tests and the T53a hook can throw there to simulate a kill. On failure the halt is lifted and the error returned; on success it stays on and the caller reloads the page, so no flush on `pagehide` can write the old game back over the new data.
